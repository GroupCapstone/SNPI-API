## 1. Original Topic Definition

> "Indicates that the request could not be processed because of conflict in the request, such as an edit conflict between multiple simultaneous updates.
"

---

## 2. In-Depth Architectural Knowledge Learned

Defines standard semantics, headers, and payload expectations for HTTP status code 409.

### Core Design Rules & Invariants:
* **Consistency**: Every API endpoint handling `http-status-409` must adhere to identical semantic contracts.
* **Client Decoupling**: Contracts must decouple client expectations from internal schema migrations.
* **Security & Isolation**: Multi-tenant scoping and authorization checks must guard `http-status-409` operations.

### Concrete HTTP Syntax / Representation:
```http
HTTP/1.1 409
```

## 4. Human & Agent Quick Reference Matrix

| Design Aspect | Standard Recommended Pattern | Anti-Pattern to Avoid |
| :--- | :--- | :--- |
| **Architectural Execution** | Return status code 409 strictly when conditions specified by RFC 9110 and guidelines are met. | Misusing 409 for unrelated semantic conditions or masking errors with 200 OK. |
| **Contract Stability** | Version and document `http-status-409` formally in `@snp/shared` | Breaking `http-status-409` behavior without migration paths |
| **Error Feedback** | Return standard RFC 7807 problem details | Silent failures or generic 500 error envelopes |
