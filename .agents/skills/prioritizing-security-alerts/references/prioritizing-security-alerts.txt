PRIORITIZING SECURITY ALERT REMEDIATION
Authors: Greg Mohler and Tom Horton
Published: August 5, 2025 | Updated: October 2, 2026
Source: GitHub Well-Architected Framework & Application Security Recommendations

1. SCENARIO OVERVIEW
Security teams face alert sprawl. Prioritizing which alerts to tackle first prevents wasted
effort and security gaps. Combining GitHub alert metadata with internal organizational context
and running structured security campaigns drives measurable risk reduction.

2. THREE-STEP PRIORITIZATION ARCHITECTURE
Step 1: Understand GitHub Alert Metadata
- Code Security (CodeQL): Severity (Critical, High, Med, Low), CWE ID, Copilot Autofix support.
- Secret Protection: Validity (confirmed active vs inactive), Provider patterns vs generic patterns.
- Dependabot: Severity, EPSS (Exploit Prediction Scoring System), Direct vs Transitive, Scope (Runtime vs Dev), Patch availability.

Step 2: Supplement with Organizational Context (Custom Properties)
- internet_facing (boolean): Publicly exposed vs internal-only.
- compliance (array): Mandates like FERPA, GDPR, HIPAA, SOC 2.
- criticality (enum): Mission-Critical, High, Medium, Low.
- user_tier / user_count: Number of active users impacted.

Step 3: Target High-Priority Alerts with Security Campaigns
- Focused, time-bound remediation campaigns with clear SLOs (e.g. 14 days for Critical + Active).
- Downstream developer notifications and centralized burndown tracking.

3. RISK SCORING INVARIANT FORMULA
CompositeRisk = BaseSeverityScore * EPSS_Multiplier * ExposureMultiplier * ScopeMultiplier * ValidityMultiplier
- Critical P0: Active secrets, runtime RCE/SQLi in internet-facing systems, EPSS > 0.5.
- High P1: High severity CodeQL/Dependabot in production with patch available.
- Medium P2: Transitive dev-dependency alerts, inactive secrets.
