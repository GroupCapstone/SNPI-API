1. CORE PROBLEM & GIT ARCHITECTURE
--------------------------------------------------------------------------------
Git stores every historical revision of every tracked file inside its local
object database.
- For plaintext files (code, JSON, markdown), Git uses efficient delta compression
  and packfiles, only storing lightweight changes between commits.
- For pre-compressed binary files (PNG, MP4, MOV, ZIP, PDF, PSD), Git cannot diff
  or delta-compress them. Every modification duplicates the entire file payload.
- Over time, binary modifications turn a 500MB repository into a 10GB+ monolith,
  degrading clone, fetch, and status operations for all contributors.

2. THE GIT LFS DECISION TRIAD (3 CRITICAL QUESTIONS)
--------------------------------------------------------------------------------
Question 1: Does the file diff?
  - Binaries (images, audio, video, compiled blobs) do not diff.
  - Plaintext files (JSON, CSV, TS, XML, CSS) produce clean line diffs.

Question 2: Does the file compress well?
  - Pre-compressed files (.png, .jpg, .zip, .tgz, .mp4, .mov) achieve < 25%
    zlib deflation; they cannot be compressed further by Git.
  - Plaintext files (.json, .xml, .csv, .sql) achieve 80% - 95% compression
    under Git's native zlib deflate algorithm.

Question 3: Does the file change frequently?
  - Frequently modified binaries duplicate storage across history.
    -> GIT LFS HIGHLY RECOMMENDED.
  - Static or rarely modified files introduce negligible history bloat.
    -> GIT LFS OPTIONAL.

3. WHEN TO USE GIT LFS
--------------------------------------------------------------------------------
1. Frequently changing binary files (video, audio, PSD mockups, 3D assets).
2. Auto-generated machine manifests not reviewed by humans (e.g. 150MB binary ASTs).
3. Excessively large historical assets not subject to human code review.
4. Large volumes of small binary assets that bloat packfile indexes.

4. WHEN NOT TO USE GIT LFS (CRITICAL CAVEATS)
--------------------------------------------------------------------------------
1. Shared Low-Bandwidth Networks with Highly Compressible Files:
   - Git compresses objects using zlib; LFS transfers raw uncompressed objects.
   - Example: 10x 150MB JSON files (1.5GB raw):
     * Native Git (85% compression): 220MB across wire (22MB per file on disk).
     * Git LFS (uncompressed): 1.5GB across wire (150MB per file on disk).
     * LFS costs 10x more network bandwidth and balloons server storage from
       2 GiB to 152 GiB!
2. Large Text Files That Change Frequently:
   - Native Git merge-ort and packfile delta compression outperform LFS full
     uncompressed object downloads.
3. Shallow Clone & Partial Clone Workflows:
   - Workflows using "git clone --depth=1" or "git clone --filter=blob:none"
     already fetch only the active commit snapshot, eliminating the need for LFS.

6. HEURISTIC & COMPRESSION FORMULA
--------------------------------------------------------------------------------
Ratio = (1 - (Compressed_Bytes / Input_Bytes)) * 100

- Ratio < 25.0% : Pre-compressed binary -> STORE IN GIT LFS.
- Ratio >= 30.0%: Compressible text     -> STORE IN NATIVE GIT.
